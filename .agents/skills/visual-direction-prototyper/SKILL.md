# Visual Direction Prototyper

Create a coherent, testable design exploration without erasing prior concepts or turning every direction into a cosmetic theme variation.

## Establish the Assignment

- Read repository instructions and existing design rationale before changing files.
- Determine whether the request modifies an existing direction or creates a new one. Preserve unrelated completed directions.
- Identify the comparison baseline: audience, content, products, required interactions, and viewport targets should remain comparable unless the user changes them.
- Treat repository documentation as the source of truth for brand-specific names, assets, and constraints.

When new or changed logos, palettes, photography, or mood boards affect the work, read [references/brand-intake.md](references/brand-intake.md) before choosing the visual system.

## Shape and Build the Direction

- State the direction's core idea, emotional register, visual principles, and meaningful contrast with existing concepts.
- Translate the idea into typography, color roles, spacing, geometry, image treatment, narrative sequence, and motion. A direction must change the experience and storytelling, not only token values.
- Use the repository's current stack unless another technology materially improves the requested result. Keep exploratory implementations isolated using the repository's naming conventions.
- Make representative commerce interactions usable: navigation, discovery, product actions, feedback states, forms, and relevant filters or search.
- Compose mobile layouts intentionally rather than compressing desktop arrangements.
- Preserve source assets. Create derived assets only when needed and authorized; document material assumptions instead of presenting inference as brand fact.

## Record the Decision

Update the repository's design record when one exists. Capture the rationale, status, palette and typography choices, interaction character, best-fit use cases, and unresolved questions. Keep project-specific rules in repository documentation rather than this skill.

Before delivery, read and follow [references/visual-qa.md](references/visual-qa.md). Report what was validated and distinguish implementation defects from preview-tool limitations.
